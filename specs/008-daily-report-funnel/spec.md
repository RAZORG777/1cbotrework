# Feature Specification: Ежедневная сводка и воронка записи

**Feature Branch**: `008-daily-report-funnel`

**Created**: 2026-10-09

**Status**: Draft

**Input**: User description: "Ежедневная сводка администратору: сколько записей, переносов и отмен
было за день, сколько подтверждений визита. Воронка в админке: сколько человек открыли форму и на
каком шаге бросили."

**Каналы**: Telegram-бот и MAX-бот считают каждый своё и шлют сводку своим администраторам
(принцип III).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Администратор получает сводку за день (Priority: P1)

Каждый день в 20:00 МСК бот присылает администраторам (ADMIN_IDS) сообщение «Сводка за 9 октября»:
новые записи, переносы, отмены пациентами и клиникой, подтверждения визита, пришедшие на приём,
новые пользователи бота, сколько человек открыли форму и сколько из них записались, сколько
записей на завтра.

**Acceptance Scenarios**:

1. **Given** наступило время сводки, **Then** каждому администратору приходит одно сообщение, в
   том числе когда за день ничего не было (видно, что бот жив).
2. **Given** бот перезапускался днём, **Then** числа в сводке не обнуляются.
3. **Given** DAILY_REPORT_TIME пустое, **Then** сводка не отправляется.
4. **Given** администратор нажал в админке «Отправить сводку сейчас», **Then** приходит сводка
   за сегодня на текущий момент.

### User Story 2 - Администратор смотрит воронку записи (Priority: P1)

Вкладка «Статистика» в админке за 7, 30 или 90 дней: воронка «Открыли форму → Выбрали филиал →
Выбрали врача и услугу → Выбрали время → Отправили данные → Записались» с числом людей и долей от
первого шага, и таблица по дням: записи, переносы, отмены, подтверждения, визиты, новые пользователи.

**Acceptance Scenarios**:

1. **Given** пациент открыл форму три раза за день, **Then** в воронке он считается один раз.
2. **Given** пациент переносит запись, **Then** воронка новой записи не меняется (перенос
   считается отдельно).
3. **Given** у пациента уже есть запись и он открыл «Мою запись», **Then** в воронку он не попадает.

### Edge Cases

- Отмену пациентом 1С подтверждает сигналом cancel-visit — она не считается второй раз как отмена
  клиникой.
- Отметка шага не должна мешать записи: ошибка /track не видна пациенту.
- Сервер не принимает неизвестные шаги.

## Requirements *(mandatory)*

- **FR-001**: Счётчики событий за день хранятся в БД (переживают перезапуск), без ПДн.
- **FR-002**: Шаги воронки считаются по уникальным пользователям за день. Для этого хранится хэш
  id пользователя, отметки удаляются на следующий день (ежедневная очистка).
- **FR-003**: Дневные итоги хранятся 400 дней.
- **FR-004**: Время сводки — DAILY_REPORT_TIME (ЧЧ:ММ МСК, по умолчанию 20:00, пусто — выключено).
- **FR-005**: Сводка без смайликов, только числа (без ФИО и телефонов).
- **FR-006**: API админки: GET /admin/api/stats?days=N, POST /admin/api/stats/report.
- **FR-007**: Форма отправляет шаги open, branch, doctor, time; submit и booked считает сервер.

## Success Criteria

- **SC-001**: Сводка приходит ежедневно в заданное время обоим ботам.
- **SC-002**: По воронке видно, на каком шаге уходит больше всего людей.
