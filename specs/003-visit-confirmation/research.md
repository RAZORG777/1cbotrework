# Research: Подтверждение визита из напоминания

## R1. Что сейчас

- **Telegram**: напоминание за 24 ч — «Оператор Call-Центра свяжется с вами для подтверждения
  записи», без кнопок; вебхук на `callback_query` только гасит «часики» (`answerCallbackQuery`).
- **MAX**: напоминание за 24 ч с кнопками `confirm_visit` / `cancel_visit_btn` (без идентификатора
  записи); «Подтверждаю» → `update_note` с текстом «✅ Визит подтвержден пациентом (MAX)» (дописывается
  в начало примечания, при каждом нажатии заново); «Отменить» → общая отмена по активной записи.
- **1С**: `UpdateNotePOST` пишет произвольный текст в примечание; у документа «Заявка» нет реквизита
  подтверждения; перечисление типов состояний: Отменена, Пришёл, Выполнена, Выполняется — типа
  «Подтверждена» нет.
- Напоминания — задания APScheduler с фиксированными аргументами (`deliver(chat_id, text, markup)`),
  текст и кнопки определяются при записи.

## R2. Способ отметки в 1С

**Decision** (владелец, 29.09; конституция 2.1.0): метод `POST confirm` HTTP-сервиса (расширение
`TGBotAPI`), тело `{"appointment_id", "platform"}`. Дописывает в **конец** примечания строку
«Пациент подтвердил запись (<Telegram|MAX>), ДД.ММ ЧЧ:ММ»; если такая строка уже есть — ничего не
пишет, `already: true`. Отменённая (состояние из `УправлениеЗаявками.СостоянияЗаявкиОтменена()`
или пометка удаления) → `code: CANCELLED`; не найдена → `NOT_FOUND`. Состояние не меняется.
Первая строка примечания («Запись из …») остаётся на месте — признак заявки бота не ломается.

**Alternatives**: новое состояние `BOT_Подтверждена` — отклонено владельцем; `update_note` —
произвольный текст, не идемпотентен, противоречит принципу II.

## R3. Кнопки привязаны к записи

**Decision**: данные кнопок содержат идентификатор заявки: Telegram `callback_data` = `c:<uuid>` /
`x:<uuid>` (≤ 64 байт), MAX `payload` = `confirm:<uuid>` / `cancel:<uuid>`. Действие выполняется,
только если это текущая активная запись пациента; иначе «Запись изменена / неактуальна».
Прежние payload MAX `confirm_visit` / `cancel_visit_btn` (сообщения, отправленные до выкладки)
продолжают работать по активной записи (FR-008).

## R4. Напоминание собирается в момент отправки

**Decision**: новое задание `send_reminder(appointment_id, kind)` (`kind` = `24h` | `2h`) читает запись
из БД в момент срабатывания: запись не активна или изменилась → не отправлять; текст и кнопки строятся
по текущим данным; при `confirmed_at` напоминание за 2 ч без «Подтверждаю». Уже запланированные
задания старого вида (`deliver`) продолжают выполняться — совместимость при выкладке.

## R5. Убрать кнопки после действия

- Telegram: `editMessageReplyMarkup(chat_id, message_id, reply_markup={"inline_keyboard": []})`;
  `chat_id` и `message_id` — из `callback_query.message`.
- MAX: `POST /answers?callback_id=…` поддерживает поле `message` (NewMessageBody) — «изменить текущее
  сообщение» (dev.max.ru, POST /answers): отправляем исходный текст + строку результата без
  `attachments` — кнопки исчезают. Лимит — не более двух ответов в секунду в диалог (у нас один).

## R6. Хранение подтверждения в боте

**Decision**: колонка `confirmed_at` (nullable) в `appointments`, схема v1 → v2:
`ALTER TABLE appointments ADD COLUMN confirmed_at DATETIME`, `PRAGMA user_version = 2`; для v0
существующая миграция создаёт таблицу сразу с колонкой. Перенос сбрасывает `confirmed_at` (как 1С
теряет пометку при перезаписи примечания). Админка показывает «подтверждена» у активных записей.
