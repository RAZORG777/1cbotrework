# Implementation Plan: Пациент и ЭМК в 1С при записи через бота

**Branch**: `002-patient-emk` | **Date**: 2026-09-25 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-patient-emk/spec.md`

## Summary

Запись из бота должна давать регистратуре пациента, по которому можно сразу оформить ЭМК.

- Метод `book` HTTP-сервиса 1С (расширение `TGBotAPI`) записывает нового клиента штатно, без
  режима `Загрузка`, и обеспечивает ему основную медкарту штатным `СоздатьМедкартуКлиента`
  с нумерацией клиники. Самодельная нумерация удаляется (R1).
- Поиск пациента: кандидаты по дате рождения, сравнение нормализованного ФИО, уточнение по
  телефону из регистра контактной информации; при нескольких совпадениях — пометка
  «проверить пациента» (R2, R3). Блокировка таблицы клиентов в транзакции исключает дубли (R4).
- Телефон нового клиента пишется штатно в контактную информацию в виде `+7XXXXXXXXXX`, а не
  в комментарий; сравнение телефонов — по цифрам (в базе форматы разные); другой
  телефон у найденного пациента — только в примечание заявки (R3, FR-004).
- Нет состояния `BOT_*` → запись не создаётся, код `STATE_NOT_CONFIGURED` (R6). Все ошибки
  `book`/`reschedule` получают машинный `code` (R7).
- `reschedule`: длительность как у записи, примечание по мессенджеру, медкарта у пациента (R5).
- Оба бота нормализуют телефон и дату рождения до `+7XXXXXXXXXX` / `YYYY-MM-DD`, проверяют их
  и понимают новые коды 1С (R8).
- Расширение `Бот_Интеграция` выводит флажки онлайн-записи на формы врача и услуги (R9).

## Technical Context

**Language/Version**: 1С:Предприятие 8.3.27 (встроенный язык, расширения конфигурации);
Python 3.12 в CI (боты, как этап 0)

**Primary Dependencies**: БИТ.УМЦ 2.0.49.101 (штатные `Справочники.Клиенты.СоздатьМедкартуКлиента`,
`ОтраслевыеДополнения.КонтрольКорректностиФИО`, `КонтактнаяИнформацияСерверПереопределяемый`);
боты — FastAPI, pydantic 2, httpx (без новых зависимостей)

**Storage**: база 1С УМЦ (клиенты, медкарты, заявки, контактная информация); SQLite ботов
без изменений схемы

**Testing**: боты — pytest, контрактные тесты клиента 1С (respx) и юнит-тесты нормализации;
1С — ручной сценарий quickstart на тестовой УМЦ (автотестов 1С в проекте нет)

**Target Platform**: сервер 1С клиники (расширения `TGBotAPI`, `Бот_Интеграция`); боты — Windows
Server, как этап 0

**Project Type**: интеграция: HTTP-сервис 1С + два независимых веб-сервиса ботов

**Performance Goals**: запись не дольше этапа 0 + 1 с (SC-005); поиск пациента — один запрос
по дате рождения

**Constraints**: основная конфигурация БИТ не меняется; 1С принимает старые и новые форматы
(выкладка ботов и 1С в любом порядке); без ПДн в журналах ботов и в ответах ошибок;
изменения контракта — одновременно в `onec/`, `docs/onec-contract.md` и обоих ботах

**Scale/Scope**: десятки записей в неделю; база клиентов — десятки тысяч; 2 метода HTTP-сервиса,
2 формы, 2 бота

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Принцип | Проверка | Статус |
|---------|----------|--------|
| I. Защита ПДн | Ответы 1С с ошибкой — машинный `code` без ПДн, текст только в журнал регистрации 1С; боты логируют `appointment_id`/`patient_id`, не ФИО/телефон (FR-015); телефон существующего пациента не перезаписывается | ✅ |
| II. 1С — источник истины | Именно цель этапа: каждая запись привязана к пациенту с номером медкарты (FR-001–003); нормализованные форматы (FR-007); код 1С и контракт — в `onec/` и `docs/onec-contract.md` (FR-013) | ✅ |
| III. Независимые боты | Нормализация и разбор кодов делаются отдельно в `telegram_bot/` и `max_bot/`, правила — в `contracts/onec-book.md`; различие только `platform` | ✅ |
| IV. Надёжность | Нет состояния → явный отказ вместо «полузаписи»; ошибки медкарты не срывают запись и видны (FR-006); блокировка от дублей (FR-012); обратная совместимость форматов | ✅ |
| V. Тесты и наблюдаемость | Контрактные тесты клиентов 1С на новые поля и коды; юнит-тесты нормализации; ручной quickstart для 1С; журнал регистрации «Бот.Запись» | ✅ |
| VI. WebApp в стиле клиники | Не затрагивается (только тексты ошибок валидации) | ✅ |

Нарушений нет, Complexity Tracking не нужен.

**Повторная проверка после Phase 1**: data-model и контракт не добавляют ПДн в ответы и журналы
(в ответ `book` добавлены только UUID пациента и признак медкарты), совместимость форматов
сохранена — ✅.
