# Feature Specification: Пациент и ЭМК в 1С при записи через бота

**Feature Branch**: `002-patient-emk`

**Created**: 2026-09-25

**Status**: Draft (уточнения 25.09 внесены)

**Input**: User description: "Этап 1 — Пациент и ЭМК в 1С УМЦ. При записи через бота метод book HTTP-сервиса БИТ.УМЦ (расширение TGBotAPI) должен находить карточку пациента по ФИО + дате рождения + телефону или создавать новую с автоматически присвоенным номером медкарты и привязывать к ней запись, чтобы регистратура могла оформить ЭМК. Боты передают телефон как +7XXXXXXXXXX и дату рождения как YYYY-MM-DD. Описать контракт в docs/onec-contract.md, код 1С — в onec/. Оба бота. Дополнительно по итогам теста 25.09: если в 1С нет состояния BOT_Первичка/BOT_Повторка — не записывать заявку с пустым состоянием; вывести флаги «Участвует в онлайн записи» на формы сотрудника и номенклатуры через расширение; перенос из MAX помечать «Перенос из MAX»."

**Каналы**: Telegram-бот и MAX-бот (оба; принцип III конституции). Изменения в 1С — в расширениях
`TGBotAPI` и `Бот_Интеграция` (основная конфигурация не меняется).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Новый пациент получает карточку с номером медкарты (Priority: P1)

Пациент, который раньше не был в клинике, записывается через бота. В 1С появляется карточка
пациента с автоматически присвоенным номером медицинской карты, и заявка привязана к ней.
Регистратор открывает заявку, переходит к пациенту и оформляет ЭМК, ничего не создавая вручную.

**Why this priority**: это основная жалоба регистратуры: сейчас по записи из бота нельзя
оформить ЭМК, потому что медкарта не создаётся никогда (research R16 этапа 0). Без этого
каждая онлайн-запись требует ручной работы на ресепшене.

**Independent Test**: записаться через тестового бота новым пациентом, открыть заявку в тестовой
УМЦ → у пациента есть основная медкарта с номером → по визиту открывается ЭМК.

**Acceptance Scenarios**:

1. **Given** в 1С нет пациента с такими ФИО и датой рождения, **When** пациент записывается через
   бота, **Then** в 1С создаётся карточка пациента с ФИО, датой рождения, полом (если его можно
   определить по отчеству) и телефоном, у неё есть основная медкарта с номером по правилам
   нумерации клиники, и заявка привязана к этой карточке.
2. **Given** пациент создан ботом, **When** регистратор открывает заявку и начинает приём,
   **Then** ЭМК оформляется без ручного создания медкарты и без ошибок про отсутствие карты.
3. **Given** создание медкарты в 1С завершилось ошибкой, **When** пациент записывается,
   **Then** запись всё равно создаётся, в примечании заявки видна пометка, что медкарту нужно
   завести вручную, а причина ошибки записана в журнал регистрации 1С.

### User Story 2 - Повторный пациент не дублируется (Priority: P1)

Пациент, который уже есть в базе (записывался через бота или приходил очно), снова записывается
через бота. 1С находит его существующую карточку и привязывает заявку к ней; новая карточка не
создаётся. Если у найденного пациента нет медкарты, она создаётся.

**Why this priority**: дубли пациентов разрывают историю болезни и ЭМК, их чистка — ручная работа.
Равно важно с US1: без поиска каждая запись порождала бы нового пациента.

**Independent Test**: записаться через бота дважды с одними и теми же данными, затем записаться
с данными пациента, заведённого вручную, → в 1С одна карточка на человека, все заявки на ней.

**Acceptance Scenarios**:

1. **Given** в 1С есть пациент с теми же ФИО, датой рождения и телефоном, **When** он записывается
   через бота, **Then** заявка привязывается к нему, новая карточка не создаётся.
2. **Given** ФИО введено с другим регистром, лишними пробелами или «е» вместо «ё», **When** пациент
   записывается, **Then** он находится так же, как при точном совпадении.
3. **Given** найден пациент без медкарты (например, созданный ботом до этого исправления),
   **When** он записывается, **Then** ему создаётся медкарта с номером.
4. **Given** найдено несколько пациентов с такими ФИО и датой рождения, **When** один из них
   совпадает по телефону, **Then** заявка привязывается к нему; если по телефону не совпадает
   никто, заявка привязывается к одному из них по правилу FR-005, и в примечании заявки
   регистратору видна пометка «проверить пациента».
5. **Given** найден пациент с такими ФИО и датой рождения, но другим телефоном, **When** он
   записывается, **Then** заявка привязывается к найденному пациенту, его карточка не меняется,
   а телефон из бота указан в примечании заявки.
6. **Given** пациент создан ботом до исправления и у него нет медкарты, **When** регистратор
   создаёт медкарту вручную из карточки пациента, **Then** медкарта создаётся с номером без ошибок.

### User Story 3 - Заявка бота всегда корректна в журнале записи (Priority: P2)

Администратор видит в журнале записи заявки бота с правильным состоянием и понятной пометкой
источника. Если 1С не настроена для приёма записей бота, запись не создаётся «наполовину»,
а пациент видит понятное сообщение.

**Why this priority**: на тесте 25.09 заявка создалась с пустым состоянием, потому что в базе
не было состояний `BOT_Первичка` / `BOT_Повторка`. Такие заявки теряются для колл-центра.
Перенос из MAX помечается как «Перенос из Telegram», и администратор не понимает источник.

**Independent Test**: удалить (переименовать) состояние `BOT_Первичка` в тестовой УМЦ и
записаться → запись не создаётся, бот показывает сообщение об ошибке; вернуть состояние →
запись создаётся с ним. Перенести запись из каждого бота → примечание указывает свой мессенджер.

**Acceptance Scenarios**:

1. **Given** в 1С есть состояния для записей бота, **When** пациент записывается на первичную
   или повторную услугу, **Then** заявка получает соответствующее состояние.
2. **Given** нужного состояния в 1С нет, **When** пациент записывается, **Then** заявка
   не создаётся, бот показывает пациенту сообщение «не удалось записаться, позвоните в клинику»,
   а в журнале бота и журнале регистрации 1С видна причина.
3. **Given** пациент переносит запись из MAX, **When** 1С переносит заявку на новое время,
   **Then** её примечание говорит «Перенос из MAX» (из Telegram — «Перенос из Telegram»),
   длительность считается так же, как при записи, а пациент заявки остаётся прежним и имеет
   медкарту.

### User Story 4 - Администратор управляет онлайн-записью из карточек (Priority: P3)

Администратор открывает карточку врача или услуги и видит флажок «Участвует в онлайн-записи».
Отметив его, он включает врача или услугу в бота; сняв — убирает.

**Why this priority**: сейчас флажок не выведен ни на одну форму, и включить врача в бота можно
только обработкой группового изменения реквизитов. Это неудобно, но есть обходной путь, поэтому P3.

**Independent Test**: в тестовой УМЦ отметить флажок у врача и услуги в карточке → врач и услуга
появляются в боте; снять → пропадают.

**Acceptance Scenarios**:

1. **Given** карточка сотрудника, **When** администратор отмечает «Участвует в онлайн-записи»
   и записывает карточку, **Then** врач появляется в списке врачей бота (при наличии графика).
2. **Given** карточка номенклатуры, **When** администратор отмечает флажок, **Then** услуга
   появляется у врачей, которым она назначена в «Основных услугах сотрудников».
3. **Given** следующее обновление конфигурации БИТ, **When** оно установлено, **Then** флажки
   на формах сохраняются.

---

### Edge Cases

- Телефон пришёл в старом формате `+7 (999) 123-45-67`, а дата рождения — `ДД.ММ.ГГГГ`
  (старая версия бота во время выкладки) → 1С принимает оба формата и нормализует телефон.
- Дата рождения не распознана или в будущем → запись отклоняется с кодом ошибки валидации,
  пациента с датой `01.01.0001` не создаётся (сейчас так происходит привязка к чужому пациенту).
- Нет отчества → пол не определяется автоматически; медкарта всё равно создаётся, регистратор
  уточнит пол при приёме.
- Две записи одного нового пациента приходят почти одновременно (двойное нажатие) → создаётся
  одна карточка пациента.
- Пациент помечен на удаление → не используется для привязки, создаётся или ищется другой.
- Перенос записи → та же заявка получает новое время, пациент в ней не меняется; если у него нет медкарты, она создаётся.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: При записи и переносе 1С MUST найти пациента по ФИО и дате рождения (без учёта
  регистра, лишних пробелов и различия «е»/«ё»), уточняя выбор по телефону, либо создать нового.
- **FR-002**: Новый пациент MUST создаваться со всеми штатными проверками и обработчиками 1С
  (нормализация ФИО, автор, дата создания), с телефоном в контактной информации и полом,
  определённым по отчеству, если это возможно.
- **FR-003**: У пациента, к которому привязывается заявка бота, MUST быть основная медкарта
  с номером, присвоенным штатным механизмом нумерации клиники; если её нет — она создаётся.
  Самодельная нумерация медкарт MUST быть удалена.
- **FR-004**: Если пациент найден по ФИО и дате рождения, но телефон отличается, система MUST
  привязать заявку к найденному пациенту, не меняя его карточку, и указать телефон из бота
  в примечании заявки («Телефон из бота: …»), чтобы регистратура могла уточнить его при визите.
- **FR-005**: Если найдено несколько подходящих пациентов и телефон не помогает выбрать, система
  MUST привязать заявку к пациенту с основной медкартой, созданному раньше остальных, и добавить
  в примечание заявки пометку «проверить пациента: найдено несколько совпадений».
- **FR-006**: Ошибка создания медкарты MUST NOT срывать запись пациента, но MUST быть видна:
  пометка в примечании заявки и запись в журнале регистрации 1С. Ошибки MUST NOT глушиться молча.
- **FR-007**: Оба бота MUST передавать телефон в виде `+7XXXXXXXXXX`, дату рождения — `YYYY-MM-DD`;
  1С MUST принимать и прежние форматы до выкладки обоих ботов.
- **FR-008**: Некорректная дата рождения MUST приводить к отказу в записи с кодом ошибки валидации;
  пациент с пустой датой рождения MUST NOT создаваться и искаться.
- **FR-009**: Заявка бота MUST получать состояние для записей бота (первичная/повторная по услуге);
  если такого состояния в 1С нет, заявка MUST NOT создаваться, а бот MUST получить код ошибки
  настройки, который показывает пациенту как общую ошибку записи.
- **FR-010**: Примечание заявки MUST указывать мессенджер-источник и для записи, и для переноса
  («Запись из Telegram/MAX», «Перенос из Telegram/MAX»); признак, по которому расширение
  `Бот_Интеграция` узнаёт заявки бота, MUST продолжать работать.
- **FR-016**: Перенос MUST рассчитывать длительность приёма так же, как запись (по услуге и врачу),
  вместо фиксированных 30 минут.
- **FR-011**: Карточки сотрудника и номенклатуры MUST показывать редактируемый флажок
  «Участвует в онлайн-записи»; флажки MUST добавляться расширением и переживать обновления БИТ.
- **FR-012**: Параллельные записи одного нового пациента MUST NOT порождать двух пациентов.
- **FR-013**: Контракт метода записи и переноса (форматы, новые коды ошибок) MUST быть описан
  в `docs/onec-contract.md`, код 1С — в `onec/`, клиенты 1С обоих ботов и их контрактные тесты
  MUST быть обновлены одновременно (принцип II).
- **FR-014**: Пациентам, созданным ботом до исправления и оставшимся без медкарты, медкарту
  создаёт регистратура вручную штатной командой карточки пациента; разовой массовой обработки
  не делается. Ручное создание медкарты у такого пациента MUST проходить без ошибок; если
  карточке не хватает данных, которые мешают этому (например, пол), 1С MUST сообщить, что
  заполнить. При следующей записи такого пациента через бота медкарта создаётся автоматически
  (FR-003).
- **FR-015**: В журнал бота и в ответы боту MUST NOT попадать ФИО, телефон и дата рождения
  (принцип I); для диагностики используются идентификаторы заявки и пациента.

### Key Entities

- **Пациент (клиент 1С)**: ФИО, дата рождения, пол, телефоны, основная медкарта. Ключ поиска —
  ФИО + дата рождения, уточнение — телефон.
- **Медицинская карта**: принадлежит пациенту, имеет номер по правилам нумерации клиники и вид
  карты; основная карта нужна для оформления ЭМК.
- **Заявка (запись на приём)**: врач, услуга, время, филиал, пациент, состояние, ответственный
  `api_bot`, примечание с источником.
- **Состояние заявки бота**: `BOT_Первичка` / `BOT_Повторка`; настраивается в 1С.
- **Флажок «Участвует в онлайн-записи»**: у сотрудника и у услуги; определяет, что видит бот.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100 % записей из обоих ботов на тестовой УМЦ создают или находят пациента с основной
  медкартой и номером; регистратор оформляет ЭМК по такой записи без ручного создания медкарты.
- **SC-002**: 0 новых дублей пациентов на 20 повторных записях одних и тех же людей (включая
  отличия регистра, пробелов и «ё»), в том числе при двойном нажатии «Записаться».
- **SC-003**: 0 заявок бота с пустым состоянием; при отсутствии настройки пациент получает ответ
  об ошибке не дольше обычной записи.
- **SC-004**: Администратор включает или выключает врача или услугу для онлайн-записи из карточки
  не дольше чем за 30 секунд, без обработок и режима технического специалиста.
- **SC-005**: Время записи для пациента не увеличивается больше чем на 1 секунду по сравнению
  с этапом 0.
- **SC-006**: После выкладки на прод регистратура за первую неделю не заводит вручную ни одной
  медкарты для пациентов из бота.

## Assumptions

- Клиника использует штатный механизм нумерации медкарт БИТ.УМЦ (вид карты, префикс, длина номера);
  если автосоздание медкарт в учётной политике выключено, бот всё равно создаёт карту штатным
  методом конфигурации.
- Основная конфигурация БИТ не меняется: изменения только в расширениях `TGBotAPI` и
  `Бот_Интеграция` (так они переживают обновления).
- Состояния `BOT_Первичка`, `BOT_Повторка`, «Отменена» и флажки онлайн-записи на проде
  уже настроены; тестовую УМЦ перед проверкой приводят к тем же настройкам.
- Пациент вводит ФИО и дату рождения сам; проверка документов — задача регистратуры при визите.
- MAX проверяется на тестовой УМЦ через клиент 1С и контрактные тесты, а в мессенджере — после
  выкладки, так как модерация MAX не пропускает тестовых ботов.
- Этап 0 (безопасность, сигналы 1С) выложен или выкладывается раньше этапа 1; этап 1 не зависит
  от нового дизайна WebApp (этап 3).

## Clarifications

### Session 2026-09-25

- Q: Пациент найден по ФИО и дате рождения, но телефон другой — что делать? → A: привязать
  к найденному, карточку не менять, телефон из бота — в примечание заявки (FR-004).
- Q: Как выдать медкарты пациентам, уже созданным ботом без карты? → A: регистратура создаёт
  вручную; массовой обработки нет; ручное создание должно работать без ошибок, при следующей
  записи через бота карта создаётся автоматически (FR-014, FR-003).
