# Quickstart: проверка этапа 1 на тестовом стенде

Стенд этапа 0: тестовый Telegram-бот на ПК с папкой 1CBOT, тестовая УМЦ
`http://192.168.13.253:8080/umc-test/hs/tgbot`, расширения `TGBotAPI` (с изменениями этапа 1)
и `Бот_Интеграция`. MAX проверяется контрактными тестами (модерация не пропускает тестовых ботов)
и после выкладки — на проде.

## 0. Подготовка тестовой УМЦ

1. Учётная политика: заполнен «Основной вид медкарт» (на тесте 25.09 — «Медицинская карта
   амбулаторного больного (Форма №025/у…) для А5», автосоздание включено). Сверить с продом.
2. Состояния `BOT_Первичка`, `BOT_Повторка`, «Отменена» есть (как на проде).
2а. Пользователь `api_bot`: филиал по умолчанию — «Профсоюзная» (его получает новая медкарта,
   research.md › R1); права на запись клиентов, медкарт и контактной информации (без них ответ
   будет `medical_card=missing`, причина — в примечании заявки и журнале регистрации).
3. Регистратура заводит вручную тестового пациента с телефоном в любом из встречающихся видов
   (`7…`, `+7…`, `+7(…)…`) — для сценария 2.3.
4. Загрузить `onec/TGBotAPI.cfe` и `onec/extension/Бот_Интеграция.cfe` этапа 1, F7,
   перезапуск 1С:Предприятие.
5. Боты: `pytest -q` в `telegram_bot/` и `max_bot/` — зелёные.

## 1. Новый пациент (US1, SC-001)

Записаться через бота на новые ФИО и дату рождения.

- Ответ `book` в журнале бота: `patient=created`, `medical_card=created`.
- В 1С: у клиента есть основная медкарта с номером по нумерации клиники; телефон виден
  в контактной информации (не в комментарии); ФИО нормализовано; заявка привязана к клиенту.
- Регистратор создаёт «Прием» по заявке и открывает ЭМК — без ошибок про медкарту.

## 2. Повторный пациент и дубли (US2, SC-002)

1. Записаться ещё раз с теми же данными → `patient=found`, новой карточки нет.
2. Те же ФИО в другом регистре, с «ё» вместо «е», с двойным пробелом → тот же пациент.
3. Пациент, заведённый регистратурой в шаге 0.3 → найден, `medical_card=existing`.
4. Тот же пациент, другой телефон → найден, карточка не изменилась, в примечании заявки
   «Телефон из бота: …».
5. Клиент, созданный ботом до этапа 1 (без медкарты) → найден, `medical_card=created`.
6. Двойное нажатие «Записаться» новым пациентом (или два запроса `book` подряд к разным врачам
   через `curl`) → одна карточка.
7. Отчёт «дубли»: в списке клиентов отбор по ФИО + дате рождения — по одной записи на человека.

## 3. Ручная медкарта у старого пациента (FR-014)

Клиент, созданный ботом до этапа 1 → регистратор создаёт медкарту из карточки клиента штатной
командой → создаётся без ошибок; если 1С просит заполнить поле (например, пол) — сообщение
понятно, после заполнения карта создаётся.

## 4. Корректная заявка (US3, SC-003)

1. Переименовать в тестовой УМЦ `BOT_Первичка` → записаться на первичную услугу → бот
   показывает общую ошибку, в журнале бота `code=STATE_NOT_CONFIGURED`, заявки нет, в журнале
   регистрации 1С — событие `Бот.Запись`. Вернуть имя → запись проходит с этим состоянием.
2. Перенести запись → та же заявка, новое время, длительность как при записи, примечание
   «Перенос из Telegram»; через контрактный тест MAX — «Перенос из MAX».
3. Отменить перенесённую запись в 1С → сигнал `cancel-visit` доходит (признак заявки бота
   работает и для «Перенос из MAX»).

## 5. Форматы и валидация (FR-007, FR-008)

- В WebApp дата `31.02.2000`, будущая дата, `01.01.1890` → бот отвечает «Проверьте дату
  рождения» до обращения к 1С.
- `curl` к `book` тестовой УМЦ со старым форматом (`+7 (999) 123-45-67`, `ДД.ММ.ГГГГ`) →
  успех; с `birth_date: ""` → `code=BAD_BIRTH_DATE`, клиент не создан.

## 6. Флажки онлайн-записи (US4, SC-004)

Карточка врача → «Участвует в онлайн-записи» снять → `curl …/doctors` без него; поставить —
снова в списке. То же для услуги и `…/services?doctor_id=…`. Засечь время: ≤ 30 с.

## 7. Производительность (SC-005)

Время ответа `book` в журнале бота (или `curl -w "%{time_total}"`) — не больше, чем на этапе 0,
плюс 1 с.
