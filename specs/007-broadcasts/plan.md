# Implementation Plan: Рассылки из админки

**Branch**: `007-broadcasts` | **Date**: 2026-10-08 | **Spec**: [spec.md](spec.md) |
**Contract**: [contracts/broadcasts.md](contracts/broadcasts.md)

## Summary

Бот ведёт список пользователей (`subscribers`) и спрашивает согласие на новости. Админка
создаёт рассылку: получатели фиксируются в `broadcast_recipients`, фоновая задача отправляет
сообщения не быстрее 20 в секунду и отмечает каждого получателя, поэтому после перезапуска
рассылка продолжается с места остановки.

## Constitution Check

| Принцип | Как соблюдается |
|---------|-----------------|
| I. Секреты | новых секретов нет |
| II. 1С — источник истины | рассылки 1С не касаются; аудитория «с записью» берётся из БД бота |
| III. Два бота | `subscribers.py`, `broadcasts.py`, вкладка админки — копии в каждом боте; отправка своя для каждого API |
| ПДн | в списке только id мессенджера и даты; заблокировавшие удаляются через `PD_RETENTION_DAYS` |

## Решения

- **Telegram-картинка**: первая отправка — `sendPhoto` multipart, из ответа берётся `file_id`
  и сохраняется в памяти задачи; остальные получатели — по `file_id`.
- **MAX-картинка**: вложение `{"type": "image", "payload": {"url": …}}` на публичный адрес
  `WEBAPP_URL/max/media/broadcasts/<имя>`.
- **Скорость**: пауза 50 мс между сообщениями; на 429 — `retry_after` (Telegram) или 1 с (MAX).
- **Блокировка**: Telegram 403 или 400 `chat not found`, MAX 403/404 → `blocked_at`. Любое новое
  сообщение от пользователя снимает отметку.
- **Остановка**: статус `stopped` в БД; задача проверяет его перед каждым сообщением.
