# 1CBOT Constitution

Боты записи пациентов клиники «ЯСНО ВИЖУ» на приём (Telegram и MAX) с интеграцией
с 1С: БИТ.Управление медицинским центром: выбор филиала, врача, услуги и времени,
запись/перенос/отмена, подтверждение визита, напоминания, отзывы, административная панель.

## Core Principles

### I. Защита персональных и медицинских данных (NON-NEGOTIABLE)

- Проект обрабатывает персональные данные пациентов (ФИО, телефон, дата рождения,
  факт записи к врачу). Обработка MUST соответствовать 152-ФЗ.
- Секреты (токены ботов, логины/пароли 1С и админки, токен вебхуков 1С, ключи TLS)
  MUST храниться только в `.env` или хранилище секретов. Секреты и пароли по умолчанию
  в исходном коде запрещены; при отсутствии обязательной переменной сервис MUST
  не стартовать.
- `.env*`, `*.key`, `*.crt`, `*.db`, логи, архивы и бинарники (`*.7z`, `*.zip`, `*.rar`,
  `nssm.exe`) MUST быть исключены из git и из архивов, передаваемых третьим лицам.
- Личность пользователя WebApp MUST устанавливаться на сервере по подписанным данным
  мессенджера (Telegram `initData` — HMAC по токену бота; MAX — аналогичный механизм
  платформы). Идентификатор пользователя из query-параметров или тела запроса
  MUST NOT использоваться для доступа к записи.
- Каждый непубличный эндпоинт MUST требовать аутентификацию: `/admin*` — логин/пароль
  из `.env`; вебхуки 1С `/api/v1/internal/*` — секретный токен в заголовке; вебхук
  Telegram — `secret_token`; вебхук MAX — механизм подписи/секрета платформы.
- Согласие на обработку ПДн MUST даваться пациентом явно (галочка не отмечена
  по умолчанию) со ссылкой на единый документ согласия клиники (`PD_POLICY_URL`,
  сейчас `https://yasno-vizhu.com/docs/Согласие_на_обработку_персональных_данных.pdf`).
- Логи MUST NOT содержать телефон, дату рождения, полное ФИО и сырые входящие
  апдейты мессенджеров; допускаются идентификаторы (`user_id`, `appointment_id`).
- Локальная копия данных записи MUST удаляться не позднее `PD_RETENTION_DAYS`
  (по умолчанию 30) дней после даты визита, отмены или сигнала `finish-visit`;
  очистку выполняет ежедневная задача. Срок хранения медицинской документации
  обеспечивает 1С, а не бот.

Обоснование: утечка медицинских данных — юридический и репутационный риск клиники;
в текущей версии любой, кто знает чужой `tg_id`, может посмотреть и отменить запись.

### II. 1С УМЦ — единственный источник истины

- Расписание, врачи, услуги, пациенты и статус записи MUST браться из 1С УМЦ
  через клиент 1С бота. Прямые HTTP-запросы к 1С в обход клиента запрещены.
- Каждая запись, созданная ботом, MUST быть привязана в 1С к карточке пациента
  (найти по ФИО + дата рождения + телефон, иначе создать с автоматически присвоенным
  номером), чтобы по визиту можно было оформить ЭМК. Запись с «незарегистрированным»
  пациентом считается дефектом.
- Бот MUST передавать данные в 1С в нормализованном виде: телефон — `+7XXXXXXXXXX`,
  дата рождения — `YYYY-MM-DD`.
- Подтверждение визита пациентом MUST менять статус записи в 1С отдельным методом
  контракта, а не текстом примечания.
- Локальная БД бота (SQLite) хранит только связку пользователь ↔ запись и служебные
  данные (задания напоминаний) и MUST NOT считаться источником истины. При расхождении
  прав 1С; синхронизация идёт через вебхуки `cancel-visit`/`finish-visit`
  без ручного вмешательства.
- Код HTTP-сервиса 1С (модули BSL) MUST версионироваться в каталоге `onec/`
  этого репозитория; изменения контракта вносятся одновременно в `onec/`,
  `docs/onec-contract.md` и в оба бота.

Обоснование: сейчас записи из бота не создают пациента с номером, и регистратура
не может открыть ЭМК.

### III. Независимые боты, единый контракт

- `telegram_bot/` и `max_bot/` — независимые приложения: свой процесс, порт, БД,
  зависимости и код. Импорт кода одного бота из другого запрещён.
- Контракт с 1С и бизнес-правила (запись, перенос, отмена, подтверждение,
  напоминания за 24 ч и 2 ч, отзыв после визита, хранение ПДн) описываются один раз
  в `docs/` и MUST одинаково соблюдаться обоими ботами. Спецификация каждой фичи MUST
  явно указывать, какие каналы она затрагивает; изменение общего правила вносится
  в оба бота в одном PR.
- Копии файлов («— копия», `.bak`, дубли каталогов вроде `telegram_bot_test/`)
  как способ версионирования запрещены; история изменений ведётся только в git.
- Тестовое окружение отличается от боевого конфигурацией (`.env`), а не копией кода.

Обоснование: владелец проекта выбрал полную независимость каналов для изоляции
отказов и выкладки; единый контракт не даёт поведению ботов разойтись.

### IV. Надёжность интеграций и уведомлений

- Каждый вызов внешнего API (1С, Telegram, MAX) MUST иметь таймаут, обработку ошибок
  и ограниченные повторы для сетевых сбоев; пользователь MUST получать понятное
  сообщение, а не трассировку или текст исключения.
- Базовый адрес Telegram Bot API (включая прокси Cloudflare Worker) MUST задаваться
  в `.env`, а не в коде.
- Задания напоминаний MUST быть персистентными (переживать перезапуск сервиса)
  и удаляться при отмене или переносе записи.
- Обработка входящих вебхуков MUST быть идемпотентной: повторный сигнал
  не создаёт дублей записей и уведомлений.
- Завершённая, отменённая или прошедшая запись MUST NOT блокировать новую запись
  пациента.

### V. Тестируемость и наблюдаемость

- Сценарии записи, переноса, отмены, подтверждения и вебхуков от 1С MUST покрываться
  автотестами каждого бота с заглушкой 1С (без обращения к боевой базе).
- Контракт с 1С MUST фиксироваться контрактными тестами; изменение, ломающее контракт
  или формат данных WebApp, MUST сопровождаться тестом нового контракта.
- CI (GitHub Actions) MUST запускать линтер и тесты обоих ботов и сборку WebApp
  на каждый PR; мерж в `main` — только при зелёном CI.
- Логи MUST писаться в файл с ротацией, с уровнем и временем события;
  подмена `builtins.print` для логирования запрещена.

### VI. WebApp в стиле клиники

- WebApp MUST визуально соответствовать сайту yasno-vizhu.com: цвета, шрифты,
  логотип и стиль карточек берутся с сайта и фиксируются как дизайн-токены.
- WebApp MUST учитывать тему мессенджера (светлая/тёмная) и работать на экранах
  от 320 px; интерактивные элементы — не меньше 44×44 px.
- Сборка WebApp — Vite + Vue 3 + TypeScript + Tailwind; в продакшене скрипты
  и стили MUST отдаваться из собранного бандла, а не с CDN (кроме SDK мессенджера).

Обоснование: WebApp — лицо клиники в мессенджере; единый стиль с сайтом повышает
доверие пациентов.

## Технологические ограничения и безопасность

- Бэкенд каждого бота: Python 3, FastAPI + Uvicorn, httpx, SQLAlchemy + SQLite,
  APScheduler (SQLAlchemyJobStore), loguru, pydantic. Все зависимости MUST быть
  перечислены с зафиксированными версиями в `requirements.txt` своего бота.
- Фронтенд: Vite + Vue 3 + TypeScript + Tailwind; отдельная сборка на каждый бот.
- 1С: БИТ.Управление медицинским центром 2.0.49.101 на платформе 1С:Предприятие
  8.3.27; интеграция — HTTP-сервис конфигурации, описанный в `docs/onec-contract.md`.
- WebApp MUST обслуживаться только по HTTPS.
- Боевой запуск — две службы Windows (NSSM): Telegram-бот (порт 8001) и MAX-бот
  (порт 8002, префикс `/max`). Установка служб и выкладка описываются скриптами
  в репозитории (`deploy/`).
- Тестовый стенд: отдельные тестовые боты Telegram и MAX и тестовая копия базы УМЦ;
  боевая база 1С для тестов не используется.

## Процесс разработки

- Репозиторий: GitHub `RAZORG777/1cbotrework`, корень — каталог проекта;
  `.gitignore` MUST покрывать секреты, БД, логи, `__pycache__`, `node_modules`,
  сборки и архивы.
- Изменения попадают в `main` только через PR с зелёным CI.
- Новые функции проходят цикл Spec Kit: `/speckit-specify` → `/speckit-clarify` →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`; план MUST содержать
  проверку соответствия этой конституции.
- Порядок реворка: (0) гигиена репозитория, безопасность и блокирующие баги →
  (1) пациент и ЭМК в 1С → (2) подтверждение визита со статусом в 1С →
  (3) новый WebApp. Каждый этап выкатывается отдельно.
- Выкладка: сначала тестовые боты и тестовая база УМЦ, затем прод вручную скриптом
  `deploy/deploy.ps1` (git pull → сборка WebApp → перезапуск служб NSSM).
